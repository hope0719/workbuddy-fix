# workbuddy-fix

macOS 本机排错的实战知识库 —— 每一条都来自真实故障现场，不是抄来的清单。

## 这个库解决什么问题

电脑"突然卡了"是最难查的一类故障：CPU 占用看起来正常，进程列表里找不到元凶，重启之后过几天又犯。原因在于**卡顿从来不是单一指标的事**，而多数排查方法只盯着 CPU 一个维度。

这个库的每份文档都遵循同一个结构：

```
症状指纹 → 四象限分诊 → 根因库匹配 → 处置与验证
```

并且强制记录**踩过的坑**。踩坑记录往往比结论更有价值——它们决定了你会不会在同一个地方浪费第二个小时。

## 三条最反直觉的结论

如果只记三件事：

1. **卡顿不一定是 CPU 忙。** 本库记录的最严重一次故障，CPU 侧完全没有异常进程 —— 罪魁是一个虚拟机静默占用了 10 GB `wired` 内存，而虚拟机内存**不计入任何进程的 RSS**。只查进程排行必然得出"没有元凶"的错误结论。
2. **`2147.48 MB` 不是写入量，是系统的日写入配额上限。** 同一天里多个无关进程都会显示 2147.5 MB / 2147.6 MB —— 它们只是各自"撞线"。**要比的是括号里的 MB/s 速率**，不是这个数字。这一条能让你的归因结论完全反转。
3. **卡顿时不要强制关机。** 如果卡顿来自 Spotlight 索引重建，强制关机会中断索引，下次开机从零再来一遍，等于白卡两次。

## 关于 `ps` / `top` 被拒绝

在部分受限执行环境（沙箱、非交互 shell、部分终端管理器）中，`ps`、`top`、`lsof`、`launchctl list` 会统一报 `operation not permitted`，即使提权也一样 —— 因为它们属 setuid 二进制，在非交互上下文执行会被系统拒绝。

本库给出的唯一可行替代方案是 **Python ctypes 直调 `/usr/lib/libproc.dylib`**，同用户进程免 root。细节与结构体陷阱见 [`macos/lag-diagnosis.md`](macos/lag-diagnosis.md) 固定坑 1–3。

## 免责与边界

- 所有命令均为只读诊断；处置动作（结束进程、卸载驱动、改电源策略）在文档中均标注风险等级，请自行判断。
- 案例数据来自作者的实机复现，不同机型、系统版本的表现可能不同，阈值仅作参考起点而非绝对标准。
- macOS 版本迭代较快，部分路径与行为随系统更新可能变化。发现问题欢迎提 Issue。
